# Smart City concurrent pipeline soak

`soak.py` observes an already running, explicit two-source **live** site. It never launches a detector, changes container limits or starts a GPU job by default. Run it after the two-source RTSP transport and native model profile have passed their bounded functional checks. The default observation interval is five seconds, default duration five minutes, and terminal progress is printed every 30 seconds.

Supply the exact site/source IDs and the active worker's NDJSON path. Managed live workers now append to `.spark/city/state/live-observations.ndjson`, with a versioned rotation manifest and two retained previous files. The reader starts at EOF and counts only new frames. It drains each sealed file before following the next manifest generation, including records appended during an EOF/rotation race. It retains bounded per-source counters, not the full recording. Finite qualification files without a manifest retain strict no-replacement/no-truncation behavior. Distinct adjacent PTS counts are unique PTS within a monotonic session; backward timestamps remain a failure.

Rotation is not permission to lose observations: a skipped generation, exceeded retention, unexpected filename/inode, rollback, truncation, partial sealed record or persistent rename/manifest mismatch fails the run. A mismatch still present more than two seconds after it was first noticed fails on a subsequent read; the normal five-second sampling interval can make detection later than two seconds. A source/worker session change still fails after startup grace, even when the new session appends to the same managed filename. Native output supports zero retained previous files, but this reader requires at least one; the managed profile uses two. Do not change retention or the active output family during a qualification run.

```sh
python tools/smart-city/soak.py --device spark \
  --site-id YOUR_ACTIVE_SITE_ID \
  --source-id YOUR_TRAFFIC_SOURCE_UUID --source-id YOUR_PEDESTRIAN_SOURCE_UUID \
  --observations .spark/city/state/live-observations.ndjson \
  --duration-seconds 7200 --trust-source-rtcp-utc --require-processed-preview \
  --ask-every-seconds 900 --container vss-agent-ui --pause-on-failure
```

The example is an explicitly requested two-hour combined test. Without `--ask-every-seconds`, the monitor makes no model requests. With it, the monitor schedules one selected-source question at a time through the existing UI `/api/vision/analyst` API, rotating the two actual source identities. It sends a live payload with a five-second recent window and waits at most the configured client timeout, capped at 55 seconds. The minimum interval is 900 seconds. It does not start a final question when the remaining observation window cannot cover that timeout. A successful response must contain an answer, grounded status, observed window and evidence tools. Receipts store answer hash/length and bounded evidence metadata; they omit answer text, source URLs and credentials. This checks a real API/evidence path, not automatic semantic correctness. It is a concurrent pipeline qualification test, not an engine latency benchmark.

`--vss-origin` defaults to the UI front door, `http://127.0.0.1:7777`. This origin serves both `/api/vision/analyst` and the `/vst` inventory proxy used for optional source-scoped pauses. Port 30888 is the VIOS facade and does not serve the UI analyst route. The other defaults are the city gateway on port 9184 and Agent on port 8100. Override origins when those services are exposed elsewhere.

`--trust-source-rtcp-utc` enables absolute source-age checks only for a source with `timestampBasis: source-rtcp`. Use it when the source clock is independently known to share the monitored host's UTC clock, such as the qualified same-host replay publisher. RTCP presence alone does not establish synchronized clocks. Without that flag, absolute age remains unknown; advancing source RTCP time is still compared with monotonic wall time. A source that merely receives duplicate old frames can therefore fail even while its gateway status remains live.

The default criteria are:

- The saved memory guard is current within 15 seconds, its floor is at least the saved reserve and 20 GiB, and both fresh OS available memory and guard available memory remain above that floor.
- Required containers remain running without recreation, a new restart, unhealthy status, changed memory limit, or an increment in cgroup v2 `oom`/`oom_kill` counters. Missing cgroup telemetry prevents a passing receipt. The default Spark set includes native detector, city gateway, Agent, VIOS processing, embedding, VLM and Spark LLM containers; repeated `--container NAME` adds other required containers. The combined example explicitly adds `vss-agent-ui` so its cgroup OOM counters and restart identity are checked alongside the preview API route. On Thor, add the actual local LLM container name explicitly.
- The gateway remains on the specified live site. Both source clocks remain RTCP based and advance; five seconds without advancement fails. Once a 30-second window is available, source-time/wall-time ratio must stay within 0.9–1.1. With trusted UTC enabled, source age must stay at most five seconds and no more than one second into the future.
- Native analytics and the shared acknowledgement agree on the active current rule revision and counter epoch. Startup grace is 15 seconds. A source clock/session change after that grace fails rather than carrying timing evidence across epochs.
- Each source emits new native frames. Over a rolling window of at least 20 frames, repeated PTS fraction must be at most 5%. Backward PTS, source-time rollback, sequence gaps and negative/non-finite position uncertainty fail. The six-class detector's ROI/event accuracy is a separate qualification task.

Thresholds have bounded CLI overrides recorded in the final receipt. A test too short to establish a complete clock window, too few new frames, or inactive native analytics cannot report success. Docker status must remain `running`: paused/nonrunning status, OOM, restarts and memory failures have no startup waiver. A healthcheck may report `starting` only before the existing warmup deadline; afterward it must be `healthy`. Unknown health values and `unhealthy` fail immediately. Containers without healthchecks remain supported through process/cgroup checks and the relevant application paths.

Output goes into a new timestamped directory under `.{device}/city/runtime/`, or the explicitly supplied new `--output-dir`. `samples.ndjson` is flushed and fsynced after each sample. Atomic `progress.json` contains current aggregate status; `asks.json` retains completed optional Ask receipts. Final `receipt.json` records pass/fail, failure reason, duration, source counts, clock ratios, memory minimum, Ask and pause receipts, criteria and evidence hashes. Failures and interruptions exit nonzero. Samples omit Docker environment and health-log bodies, full frame objects and private RTSP URLs.

`maximumDuplicateFractions` includes all sampled windows, including startup grace. `maximumPostWarmupDuplicateFractions` includes only windows evaluated by the duplicate pass/fail gate: after startup grace with at least 20 new frames. These rolling windows can include frames received during grace; the window and 5% threshold are unchanged. A startup-only peak above 5% can therefore appear in a passing receipt, while every gate-evaluated window must remain within the limit. `monitorSourceSha256` is captured when the monitor module loads, before sampling or request workers start, so an edit made during a run cannot change that run's recorded script hash.

`--require-processed-preview` adds a separate, opt-in exact-frame delivery qualification. Without this flag, the monitor does not read preview binaries or require preview health. With it, use a sample interval of at most five seconds. Each sample requires both explicit source IDs to be ready/available in gateway `processedPreview` health, and native delivery to be enabled, fresh within five seconds and nonfailed after startup grace. The global accepted-frame counter and each source's native published counter must advance within five seconds. A counter decrease or preview engine/native session or model change after grace fails with an explicit epoch/reset reason. Resets seen during grace are counted and can recover; they do not silently join two epochs into one timing claim.

Every five seconds, this mode reads one latest binary pair per source through the UI origin at `/api/vision/city/preview/{sourceId}`. Reads use a three-second network timeout/deadline, reject redirects and cap the complete response at `4 + 512 KiB JSON + 2 MiB JPEG`. Independent parsing verifies the big-endian length prefix, JSON schema, site/source, exact engine and native session, sequence, source time, model, original image dimensions and provenance against the envelope's matched history snapshot. It checks JPEG SOI/EOI and SOF dimensions without image decoding. Proportional downscaling is accepted; an aspect or original-geometry mismatch fails. The source's live session/model/geometry must also match. A higher sequence with an equal source timestamp remains a distinct frame; the same sequence cannot claim a different timestamp. The fetched identity must advance within five seconds after grace, even when source status and delivery counters still look healthy. A passing run requires at least two successful binary reads for each source.

Preview metrics retain only bounded identity, dimensions, byte counts, SHA-256 hashes and delivery/drop counters. JPEG bytes and full paired snapshots are never saved. Explicit display drops, network post failures and queue overruns remain diagnostic counters while fresh accepted/published frames and exact identities continue to advance. This gate establishes current exact inference-frame pairing and delivery, not browser rendering at 15 FPS, physical capture latency, visual detector correctness or semantic event accuracy. The existing source-clock, memory, OOM and native-analytics checks remain active.

`--pause-on-failure` is an explicit operational action. It resolves exact source names from VIOS inventory and requests the canonical Agent `POST /api/v1/rtsp-streams/{id}/analysis` action `pause` for **only** the specified source IDs. It attempts both even if one request fails and records each receipt. It does not delete sources, stop unrelated containers or change budgets. Without the flag the monitor only reports and exits.

Pause receipts distinguish HTTP completion (`requestCompleted`) from confirmed source state (`pauseConfirmed`). An Agent response can return HTTP 200 with partial cleanup. Confirmation requires the requested source/action, paused state, inactive analysis, and successful detection and embedding cleanup steps. Inspect unconfirmed pauses; a completed HTTP request alone is not proof that analysis stopped.

To permit cancellation of observation while keeping the live demo running, add `--cancel-file .spark/city/runtime/my-soak.cancel` when starting the observer. Use a unique marker path for each run. Later, request cancellation without signalling the process:

```sh
touch .spark/city/runtime/my-soak.cancel
```

The marker's contents are never read. An already-existing marker cancels before the first observation. The observer checks cooperatively between bounded work units; cancellation cannot interrupt an HTTP request already in progress. A sample already being checked is validated and saved before cancellation, and a real failure found in that sample retains its ordinary failure-pause behavior. No new scheduled Ask starts after cancellation is observed. Use a fresh marker name for each run; the observer does not delete markers.

Cancellation writes an explicit non-pass receipt: `passed: false`, `cancelled: true`, `failure: monitor-cancelled-by-request`, and final progress `status: cancelled`. It exits nonzero and never requests source pauses through this cancellation path, even with `--pause-on-failure`. An Ask already running cannot be retracted by cancelling its Python future; `cancellation.pendingAskMayFinish` discloses that case. The process may remain alive until that bounded client request finishes, and the server can finish already-submitted work. This is not a successful qualification. SIGINT/SIGTERM retain their existing interruption/failure behavior, including source pauses when requested; the marker is the explicit opt-in alternative.

CPU controls run from the existing development/test Python environment without contacting Docker, the gateway, Agent or a model:

```sh
python3 -m pytest -q tools/smart-city/tests/test_soak.py \
  tools/smart-city/tests/test_soak_preview.py tools/smart-city/tests/test_soak_cancel.py
```
