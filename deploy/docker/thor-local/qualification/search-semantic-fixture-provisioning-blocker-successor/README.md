# Search semantic fixture provisioning blocker successor

This additive package answers one narrow question before any more Search
runtime authority is granted: can the current production APIs safely create,
use, and exactly remove the full fixture required by
`search-semantic-runtime-evidence-successor`?

The source-locked answer is **not yet**. The package therefore does not add a
runtime executor, bind the selected Search oracle, or reinterpret an
operator-provisioned fixture as executor-owned. Its default and only command
is an inert compiler:

```bash
python3 deploy/docker/thor-local/qualification/search-semantic-fixture-provisioning-blocker-successor/compiler.py plan
```

The compiler reads reviewed repository files, validates 18 exact SHA-256
locks, checks the selected 500-row Search oracle is still open and null-bound,
checks the predecessor remains 14/14 and non-promoting, and checks the
production semantics behind every blocker. It performs zero runtime requests
and zero runtime actions. It imports no network, Docker, subprocess, or
credential client and exposes no execute mode.

The nine-entry adapter sequence is a total planned-action inventory, not a
successful execution path: two entries are blocked and four are only partial.

## Why direct Elasticsearch setup is not enough

An exact Elasticsearch-only adapter is mechanically possible: preflight six
document IDs, bulk-create them with `op_type=create`, verify exact source
digests, reverse-delete those six IDs, then verify delayed absence and a
foreign sentinel. That lifecycle is recorded as the maximal exact subset, not
as a full fixture.

The Search routes need more than raw tuples:

- VST allocates its own `sensorId`; the current upload inputs do not request
  the predecessor's digest-pinned sensor identity.
- the selected-object route requires the predecessor's exact object, sensor,
  stream and timestamp tuple;
- RTVI-CV registration silently skips connection and timeout failures, so a
  successful upload-complete response is not proof of CV fixture creation;
- attribute result processing resolves sensors through VST and can discard
  otherwise matching Elasticsearch hits when that resolution fails;
- query embeddings are generated by the configured services and the strict
  public `SearchInput` does not admit explicit query vectors;
- the shipped Search/Thor-full configs use fixed behavior/raw index names,
  while the predecessor derives run-namespaced indices; and
- video deletion is best-effort across systems and can report partial/failure.
  Its Elasticsearch portion uses field-based `delete_by_query`, not the
  predecessor's six exact document tuples.

Consequently, wrapping the 14-action candidate with a bulk create would prove
only that Elasticsearch accepted JSON—not that the functional Search fixture
was created or exactly removed. The contract lists six concrete requirements
for a future additive execution-envelope successor.
